1. Project overview

EquipRent is an equipment-rental marketplace, initially oriented to Hyderabad. The repository contains independent Expo customer and partner apps; the partner binary serves owners and operators. Marketing and the platform-operations console are separate repositories. This is an API migration/design problem: there is no standalone Node.js API implementation in the supplied project.

Observed stack: TypeScript, React Native, Expo Router, pnpm workspaces, Supabase JS, PostgreSQL 17 configuration, Supabase Auth/Storage/Realtime, SQL functions/triggers/RLS, pg_cron and some pg_net scaffolding. The current package manifest specifies Expo ~57.0.27, React 19.2.3 and React Native 0.86.3; older README version tables are stale. Jest, Node tests, Playwright tooling and isolated SQL suites already exist.

The client path is screen → hook/context → service → direct PostgREST/RPC, Auth, Storage or Edge Function. Services expose snake_case row contracts and contexts often map them to camelCase. Existing services have mixed return/error conventions and recovery reads after uncertain writes; a migration adapter must preserve those semantics until clients change.

Local inventory: 243 SQL migration files and five Edge Function entry points: razorpay-payment, razorpay-webhook, operator-access-payment, mobilization-quote, and customer-account-session. The supplied audit snapshot reports 114 application tables and 591 functions; those are snapshot claims, not a fresh hosted measurement. A separate untracked normalized proposal describes 120 tables across 16 business schemas. It is not the current runtime schema.

3. Recommended Node.js architecture

Recommendation: TypeScript + Fastify modular monolith, PostgreSQL, and a separately runnable worker. This fits the existing functional-handler proposal and SQL-heavy domain better than an immediate microservice or ORM rewrite. Use Node.js 24 LTS for the initial compatibility baseline, pinning a tested patch and dependency lockfile at implementation. The official release page currently labels Node 24 LTS and Node 26 Current; recheck at kickoff. Node release policy.

Register shared packages in pnpm-workspace.yaml deliberately; the existing workspace includes apps/*. Keep backend dependencies and secrets out of Expo bundles. Controllers remain thin; services coordinate transactions and policies; repositories never accept arbitrary SQL/table/RPC names from callers.

Transaction boundary: authenticate → resolve verified principal to selected account → validate DTO → begin transaction → set trusted transaction-local actor context → authorize resource and lock/version-check → perform state/ledger changes → append audit/outbox → commit → return. Use the same checked-out client for every statement, release in finally, and rollback on failure. node-postgres transactions. Do not call remote payment/routing/SMS providers while holding database locks.

Two legitimate migration paths: (A) retain Supabase Auth and use caller-scoped RPC through an adapter first, preserving RLS; move carefully to direct pg only after reproducing session/claims semantics. Do not proxy every request through the service-role key. (B) replace Supabase with chosen infrastructure: map verified issuer+subject to internal actor/account IDs, port auth.users FKs/auth.uid()/grants and session checks, migrate storage/realtime/cron, and run actor-matrix tests. Existing AWS plans suggest Cognito, PostgreSQL/RDS, object storage and an API/worker deployment, but this assessment does not provision or select that cloud path.

Event delivery: initially preserve Supabase Realtime behind a client subscription adapter. SSE is a proposed replacement for server-to-client updates; support chat sends continue over REST. Use domain invalidations plus authorized read-back, durable sequence/cursor, reconnect backoff and explicit resync on event retention expiry. Reauthorize on membership changes and token expiry.

4. Proposed REST contract and endpoint catalogue

Every path below is proposed, not an existing Node route. “Parity” means the underlying workflow exists in reviewed source; it does not mean the HTTP DTO or permission contract is finished. Optional/recommended additions and staff contracts needing external-console review are labeled separately. This is the complete recommended route inventory for the reviewed customer/partner workflows and evidenced staff operations; it is not a completeness claim for repositories outside the supplied folder. A route with a finite action/kind enum covers only the listed commands, never arbitrary SQL/RPC execution.

Refinement delivered: OpenAPI 3.1.1 draft for 13 operations covers saved addresses (4), public machine search/detail (2), checkout holds (2), and notifications (5). It includes explicit schemas, query serialization, responses/errors, bearer requirements, source file/line anchors, business rules and proposed changes. The other 253 entries remain an inventory for detailed contract work, including identity issuance and staff authorization. This is a deliberately bounded draft, not a complete OpenAPI definition for the whole product. The selected format follows the OpenAPI 3.1.1 specification. See static contract checks and unverified items.

Acceptance criteria: 28 planned contract cases cover duplicate addresses, partial/null updates, same-phone account isolation, public projection leakage, search bounds and date limits, concurrent holds, expired-hold recovery, notification response shapes and cursor behavior, and session replacement versus authority outage. They are not executed tests; booking-submit cases are explicitly outside the detailed OpenAPI subset pending the full booking DTO. The draft includes illustrative request and response examples, without real credentials or identities.

Notation: P = path parameters; Q = query parameters; B = JSON body; H = header. A = authenticated, admitted account with active device session; C = customer; O = owner; Op = operator; B in the authorization column = authorized booking participant, with role-specific field projection; G = guest-safe read; S = staff with both capability and resource scope. Public/OTP routes have rate limits but no bearer requirement. Resource IDs are UUIDs unless explicitly catalogue codes, provider order IDs or operator codes.

Participation is not blanket access: B is shorthand for an operation-specific policy to be derived from the effective SQL. It never grants every customer, owner or assigned operator the full booking row, finances, evidence or custody codes. Operators already use restricted projections and money-free inbox snapshots. Staff capability names in the broad catalogue are proposed mappings, not verified grants; validate them against the external console before implementation.

Common response/error contract: successful JSON wraps the stated payload as {data:..., meta:{requestId,...}}; lists use {data:[...],page:{limit,nextCursor},meta:{requestId}} except explicitly retained limit/offset searches. 204 has no body. Error responses are {error:{code,message,details?},requestId}, with sanitized field errors only. All routes may return 400 malformed request, 413 body too large, 415 wrong content type, 422 invalid fields, 429 throttled (Retry-After), 500 unexpected failure or 503 unavailable. Protected routes also return 401 invalid/expired/replaced session, 403 forbidden action, and 404 missing/non-visible resource; avoid existence disclosure. The catalogue adds each route's domain errors. Infrastructure probes use their documented minimal response rather than the JSON envelope.

Pagination: Page = {limit?:1..100,cursor?:opaque}, default 25 proposed, stable (created_at,id) ordering for history. Cursor binds the filters/sort and is validated. Existing catalogue/reviews expose offset; preserve that during parity, cap depth and add appropriate keyset/search-session semantics later. Do not silently replace the existing “total” with an estimate. GET requests have no body.

Recommended write protocol: strict allowlisted schemas, unknown fields rejected, Content-Type application/json, Idempotency-Key required on booking/payment/custody side effects and recommended on other retryable creation commands. Store actor+operation+key+canonical request hash+receipt atomically; different payload reusing a key → 409. These HTTP idempotency and version fields are proposed additions unless the source explicitly implements them; current checkout request IDs deduplicate submissions but do not compare a stored request hash. Hold acquisition uses its existing actor/window semantics without a required Idempotency-Key. Use expectedVersion/revision on mutable negotiations; return current version on authorized conflicts. Quote IDs are checked for actor, machine, destination, tariff/version, expiry and amount.

Custody authorization matrix: pickup code is held by the owner and verified by assigned operator or eligible machine-only customer; site handover code is held by customer and verified by assigned operator; release code is held by customer and verified by assigned operator after financial clearance; dropoff code is held by owner and verified by assigned operator or eligible returning customer. Validation: enforce UUID/code formats, E.164 normalization, bounded text/arrays, paired valid date ranges, positive integer quantities, finite bounded coordinates, nonnegative prices with explicit scale, finite enumerations and cross-field exclusivity. Authorization: establish a route/action/resource/field matrix and deny by default. Apply policy in service and database. Use restricted non-owner runtime DB roles without BYPASSRLS; transaction-local verified context, safe search_path and restricted EXECUTE for privileged procedures. Table owners usually bypass RLS, so merely enabling it is insufficient. PostgreSQL RLS. Staff finance/dispatch/contact access must retain capability and geography/booking scope, not become a universal admin bypass.

API hardening: TLS, secure headers, exact CORS origins, trusted-proxy configuration, body/upload/query/time limits, strict server-owned schemas and parameterized SQL. Escape text at presentation; do not use lossy “sanitize everything” rules for names or evidence. Prevent SSRF by accepting server-issued file IDs rather than arbitrary fetch URLs. Use bearer auth in mobile secure storage; if browser cookies are chosen, add Secure/HttpOnly/SameSite and CSRF protection. CORS is not authorization.

Rate-limit recommendation, to tune: OTP send at most one per phone per 60 seconds plus rolling phone/device/IP budgets; bounded verification attempts per challenge; tighter custody-code, payment-order, upload and support-message limits; cheap per-actor position limits and per-connection event caps. Distributed replicas must share counters. Do not rely on the existing client auth cooldown to stop direct API abuse. Avoid rates that prevent validated provider webhook retries.

Secrets and privacy: environment-specific managed secrets, workload identity where available, rotation and startup validation; never place database/service-role/Razorpay/webhook/routes secrets in EXPO_PUBLIC variables. Do not log JWTs, phone OTPs, custody codes, phone numbers, KYC contents, bank data, raw evidence, signed URLs or precise movement trails. Public photos can be cached; KYC, condition and identity media require fresh authorization and short-lived URLs. Scan/quarantine uploads and strip unnecessary public-photo metadata; retain original evidentiary material according to approved policy.

Audit: append actor/account/session, action, subject, timestamp, request/causation IDs, policy/version, result and safe before/after data for bookings, prices, custody, staffing, verification, document/contact access, financial changes, moderation and deletion. Separate security logs from customer-visible business history; restrict log access and retention. Object evidence should not be overwritten; corrections append new records.

Payment integrity: preserve raw webhook bytes, verify HMAC with constant-time comparison, deduplicate by provider event ID and payment/order uniqueness, check captured amount/currency/obligation, tolerate duplicate and out-of-order delivery, and acknowledge only after durable inbox persistence. Capture may arrive after a failed client return; financial terminal states cannot regress. Reconciliation handles ambiguous provider timeouts. Razorpay webhook guidance.

Versioning: /v1 plus versioned schemas, additive compatible evolution, deprecation telemetry and a tested mobile compatibility window. Server policy snapshots and consent versions are independent of URL versions. Use expand/contract DB migrations; do not drop fields while older supported apps/admin callers still depend on them.
